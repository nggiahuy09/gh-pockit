# ADR 0001 — Use Drift as the local source of truth

## Status

**Accepted** — 2026-09-16 (W2 T4). Drafted 2026-09-12 (W1, weekend flex);
amended 2026-09-14 (W2 T2) and 2026-09-15 (W2 T3).

The condition this ADR set for itself is met: `create → watchAccounts emit`
passes, as the first test in
`test/features/accounts/data/daos/account_dao_test.dart`. A row written through
`AccountDao.insertAccount` reaches a `watch()` subscriber with nothing
invalidating the query by hand — which is the whole claim golden rule 1 rests
on, and the one thing that would have made this decision wrong if it had not
held. All three open questions were answered at T2 and T3 and are recorded
below.

W2 T2 landed the store: `pubspec.yaml` carries Drift, `GPAppDatabase` exists
with a `settings` table, and four tests in
`test/core/database/database_test.dart` exercise the first queries. W2 T3 added
`accounts` at `schemaVersion` 2 and, with it, the first real migration — the
claim in constraint 3 below stopped being a promise and became
`test/core/database/migration_test.dart`.

> **On the number.** 0001 is the slot Appendix E of `docs/blueprint.md` reserves
> for this decision, and ADR-0002 recorded it as a deliberate gap rather than an
> oversight. The gap is now closed.

## Context

`CLAUDE.md` golden rule 1 already commits the app: _the local DB is the source
of truth for the UI, and the UI never reads a network response directly._ That
is settled. What is not written down anywhere is **which** local store carries
that role, and why the obvious alternatives cannot.

W2 starts on Monday and its first task installs the store. Choosing it in a
commit message is how the reasoning gets lost, so it is chosen here.

The store has to satisfy six constraints, each traceable to an existing rule
rather than to taste:

1. **Reactive queries.** Rule 1 plus anti-pattern §12.1: a write from anywhere —
   a user tapping save, a sync pull applying a delta — must repaint the list
   with no manual refresh. The store must emit on change, at query granularity.
2. **Multi-table transactions.** Golden rule 3: the entity write and its outbox
   mutation commit in the _same_ transaction, because a crash between them is
   data that never syncs. This needs real ACID across tables, not per-box
   atomicity.
3. **Versioned migrations.** Golden rule 7: never wipe the database on a schema
   change; every version bump needs a migration and a fixture test (W9 is an
   entire week of this).
4. **Indexed aggregate queries.** §6 forbids storing derived balances and
   requires computing them with an indexed aggregate; §12.8 names hard-stored
   balances as an anti-pattern; W8 benchmarks all of it at 50 000 rows. This
   needs SQL — `GROUP BY`, composite indexes, and `EXPLAIN QUERY PLAN` to prove
   the index is used.
5. **Execution off the UI isolate.** §6 puts heavy queries on a background
   isolate.
6. **Distinct row types.** The three-model rule says DB row ≠ DTO ≠ entity. A
   row type generated from the schema is what makes a mapper's correctness
   something the analyzer can check instead of something a reviewer has to
   notice.

## Decision

**Drift 2.31.0 with `drift_flutter` 0.2.8, over SQLite, as the only persistent
store for domain data.**

> **On the versions.** This ADR was drafted against `CLAUDE.md` §5, which said
> 2.34.x / 0.3.x. Neither resolves: `drift` ≥2.33.0 and `drift_flutter` ≥0.3.0
> both require Dart ≥3.10, and `.fvmrc` pins 3.9.2. The SDK pin wins, as it
> already does for `go_router`. `drift_dev` tracks `drift` at 2.31.0 and
> `build_runner` resolves to 2.15.1. §5 has been corrected.

- Tables are declared in Dart and the schema is generated by `build_runner`.
  The generated row classes (`TransactionRow` and friends) are one of the three
  models — mapped out of, never shared with the DTO or the entity.
- Every read that feeds the UI is a `Stream`, from a `watch*()` query. This is
  what makes rule 1 the path of least resistance rather than a discipline
  somebody has to remember.
- The `sync_mutations` outbox lives in the **same** database as the entities.
  That is the whole reason golden rule 3 can be a single `transaction {}` block
  instead of a two-phase commit between two stores that cannot agree.
- Migrations use `MigrationStrategy`, with fixtures produced by
  `drift_dev schema dump` and verified by `drift_dev schema generate` — both
  commands are already in `CLAUDE.md` §9, ahead of the code they will run on.
- Background execution is `drift_flutter`'s default — `driftDatabase()` opens
  through `NativeDatabase.createBackgroundConnection`, so queries never run on
  the UI isolate whatever we do. What we add is
  `DriftNativeOptions(shareAcrossIsolates: true)`; see open question 2 below
  for what that actually buys.
- **No `sqlite3_flutter_libs`.** It and `sqlcipher_flutter_libs` are EOL in the
  current setup (blueprint §58); `drift_flutter` brings its own native setup.
  If database encryption lands in P7/W23 it goes through the
  SQLite3MultipleCiphers build hook, and this decision must not foreclose that.

### What also goes in Drift, and what does not

Local settings — the language choice from ADR-0004, and whatever joins it — go
in a `settings` table in this same database, not in `SharedPreferences`. One
persistent store means one place that can be inconsistent after a crash, one
backup story, and one thing to migrate.

Auth tokens do **not**: they belong in `flutter_secure_storage`, because that is
an OS-keystore concern rather than a data-modelling one.

## Alternatives

**Hive / Isar (NoSQL document stores).** Rejected on constraint 4 first: with no
SQL there is no aggregate, so "spend per category per month over 50k rows"
becomes load-everything-and-fold-in-Dart — precisely what §6 forbids and W8
measures. Constraint 2 finishes it: no transaction spanning two boxes means
golden rule 3 cannot be enforced at all, only hoped for. Maintenance is a
secondary concern in both cases and not the deciding one.

**`sqflite` with hand-written SQL.** The closest real contender — it satisfies
2, 3 and 4 outright. It fails 1 and 6: there are no reactive queries, so every
screen needs a hand-rolled `StreamController` plus manual invalidation, and the
bug that produces is specific and nasty — _the sync pull wrote rows and forgot
to invalidate_, leaving a UI that is silently stale exactly when the app is
doing the thing it exists to do. There is also no generated row type and no
migration-test tooling. The end state is a worse Drift, written here.

**`SharedPreferences`.** Named only because the blueprint's FAQ (§53) asks the
question. It is not a database: no transactions, no queries, and a whole-file
rewrite per change.

**ObjectBox.** Fast and reactive, but adds a native binary per platform and has
a weaker story for the fixture-based migration testing W9 is built around.

**`floor`, `sqlcool`, and similar.** Thinner ecosystems and weaker migration
tooling, for no advantage over Drift on any of the six constraints.

## Consequences

**Positive**

- Golden rule 3 collapses to one `transaction {}` block — the hardest rule to
  follow becomes the easiest thing to write.
- Rule 1 is the default: `watch()` is the natural API, so the API-driven-UI
  anti-pattern takes deliberate effort to commit.
- `NativeDatabase.memory()` makes every repository test hermetic and fast, which
  is what §8 asks for when it requires repository tests on an in-memory DB.
- `EXPLAIN QUERY PLAN` is available, which is what turns W8's "480ms → 12ms"
  soundbite into a measurement rather than a claim.
- Migration testing has first-class tooling instead of a hand-rolled harness.

**Negative**

- `build_runner` joins the loop. Every schema edit needs codegen, and generated
  files are excluded from analysis — already configured in
  `analysis_options.yaml`, ahead of the first generated file.
- Generated output is **committed**, not gitignored. CI runs no codegen step
  (`.github/workflows/ci.yml` is format → analyze → test), so an uncommitted
  `database.g.dart` is a red build. The side benefit is the one this repo cares
  about: a schema change shows up in the PR diff as actual SQL, which is what
  makes "did this need a migration?" a reviewable question rather than a
  remembered one.
- `dart format` and the generator disagree about line width — the generator
  writes at 80, `formatter.page_width` is 180, and `dart format` has no exclude
  option — so `dart run build_runner build` must be followed by
  `dart format .` or the pre-commit hook fails on a file nobody wrote.
  `CLAUDE.md` §9 chains the two commands for this reason.
- Migration correctness becomes a permanent responsibility. After W9 no schema
  change is ever one line again.
- Drift's API spreads through `data/`. Replacing the store later is a real port,
  not a config swap. Accepted deliberately: the thing that protects the rest of
  the app is the repository interface in `domain/`, and wrapping Drift in a
  second abstraction to hedge against a migration that will probably never
  happen is the day-one over-engineering §12.11 rejects.
- Cold build time grows with codegen.

## Settled in W2 T2 (2026-09-14)

**2. When the background isolate lands — answered: now, and the question was
mis-framed.** Reading `drift_flutter` 0.2.8 shows the database is _already_ off
the UI isolate by default, through
`NativeDatabase.createBackgroundConnection`. There was never an isolate to
"land"; §6 is satisfied out of the box. The real choice is
`shareAcrossIsolates`, which decides whether a _second_ isolate opening the
same database name joins the same instance or opens a competing connection to
the same file. It is now `true`. Two consequences that would have been painful
to retro-fit: `workmanager` background sync in P4 gets the same instance
instead of racing the UI connection for the write lock ("database is locked"),
and a stream query in the UI learns about rows a background pull wrote. The
cost is a small overhead forwarding table updates between isolates, and the
constraint — nothing unsendable may cross the boundary — now applies to every
DAO from the first one rather than to four of them at W7.

**3. Typed `settings` table or key/value — answered: key/value.** Typed columns
are the better shape once the columns are known; today they are not, and
finding out later costs a `schemaVersion` bump, a migration and a fixture test
_per setting_. What key/value buys in exchange is a `String` parsed by hand,
and that risk is bounded: this table is local-only and holds nothing that is
money, an id, or anything sync reads. A setting that needs a real type earns
its own table rather than a `switch` on this one.

## Settled in W2 T3 (2026-09-15)

**1. `owner_id` before auth exists — answered: a sentinel, and the column is
`NOT NULL` from the first insert.** Synced rows written before W10 carry
`localOwnerId` (`'local'`, in `core/database/owner_id.dart`). The alternative —
nullable now, backfilled and tightened at W10 — was rejected on two counts. It
would make every DAO, query and sync path written between W2 and W9 tolerate a
null owner, which is eight weeks of code shaped around a temporary state; and
tightening a column to `NOT NULL` in SQLite is a full table rebuild, not an
`ALTER`. It would also leave the local schema disagreeing with the Postgres
mirror of W10 T3 for exactly the period sync is being designed in.

The risk this ADR named is not dissolved, only bounded: `NOT NULL` is enforced
today, but _a real uid flowing through the column_ is not proven until W10.

Worth stating because it changes what W10 owes: claiming these rows is **not** a
schema migration. It needs the uid, which only exists at runtime after a
sign-in, so it cannot live in an `onUpgrade` step — it belongs in the sign-in
flow as `UPDATE … SET owner_id = :uid, updated_at = :now, version = version + 1
WHERE owner_id = 'local'`, after which the rows enqueue as ordinary create
mutations. That step has to exist regardless: a user who tracks expenses offline
for a week and only then registers must keep the week. The sentinel is not
buying a migration on credit; it is naming work that was always required.

**The v1 → v2 bump was taken the expensive way.** Golden rule 7 permits wiping
the database during Phase 0–1 and `settings` held one language preference, so
the cheap path was available and was refused. W9 is an entire week of migration
work, and that week needs an earlier schema that genuinely exists. Taking the
exception would have meant the first migration Pockit ever writes being written
in W9, against a user's database, with no fixture to have practised on. v1
survives in `drift_schemas/drift_schema_v1.json` as something to upgrade rather
than something to delete.
