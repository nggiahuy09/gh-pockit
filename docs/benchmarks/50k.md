# 50k transactions — and what W9 T6 changed

Measured on 2026-11-04 (W9 T5 and T6), on Flutter 3.35.6 / Dart 3.9.2 and SQLite 3.54.0. The dataset is 50,000 transactions over the 24
months up to the run, 1,036 of them tombstones, from seed 42 (ADR-0025). A month holds about 2,100 rows, which is the worst case for the
month queries.

"Before" means schema v4 and the eager day cards. "After" means schema v5 with the covering account indexes (ADR-0027) and the lazy day
cards (ADR-0028).

## Host — query tier

This tier runs on a MacBook in JIT, so compare it only with other host runs. The cases come from ADR-0026, and the times are the repository
median: the first emission a bloc receives, mapped.

| Case | Rows | Before | After |
| ---- | ---: | -----: | ----: |
| List, newest 50 | 50 | 2.06 ms | 2.17 ms |
| List, newest 500 | 500 | 16.5 ms | 16.5 ms |
| List, newest 2,000 | 2,000 | 85.1 ms | 87.3 ms |
| List, busiest account | 50 | 2.12 ms | 1.98 ms |
| List, quietest account | 50 | 3.58 ms | 3.41 ms |
| List, account with 3 rows | 3 | 14.9 ms | 15.2 ms |
| List, busiest category | 50 | 1.92 ms | 2.03 ms |
| Month totals (Home) | 1 | 0.65 ms | 0.66 ms |
| Month spending by category (Home) | 10 | 1.70 ms | 1.59 ms |
| **Account balances (Home, Accounts)** | 6 | **26.8 ms** (p90 35.5) | **5.01 ms** (p90 5.41) |

Seeding 50k rows took 985 ms before and 991 ms after. The wider indexes cost no measurable write time.

### The slowest query (T5)

The slowest query is the account balances. It is the only query here that grows faster than the history, and it re-runs on every
transaction write (ADR-0019). Going from 10k to 50k is five times the rows, and its time went from 2.84 ms to 26.8 ms.

Before, its plan sought each account index and then read the table row for `type`, `amount_minor` and `deleted_at`:

```
SEARCH a USING INDEX accounts_owner_id_is_archived (owner_id=? AND is_archived=?)
CORRELATED SCALAR SUBQUERY 1
SEARCH t USING INDEX transactions_account_id_occurred_at_id (account_id=?)
CORRELATED SCALAR SUBQUERY 2
SEARCH t USING INDEX transactions_destination_account_id_occurred_at_id (destination_account_id=?)
USE TEMP B-TREE FOR ORDER BY
```

At 50k, those row reads miss the 8 MB page cache, because the file is 27 MB. After the change, both sides read `USING COVERING INDEX` and
no table row is read. ADR-0027 records the options and why the existing indexes were widened rather than new ones added.

The runner-up is the account with 3 rows, at 15 ms. Its list has too few rows to fill a page, so the plan walks the whole owner index.
That is the "before" for the `UNION ALL` of W4 T5. It is not urgent: few accounts are that sparse, and 15 ms on the host does not block a
frame.

## Device — Android emulator `Pixel_10`, profile

The user chose the emulator to finish the week (ADR-0026, amended). Its numbers vary up to three times between runs, and its raster thread
is the emulator's own. Compare them only with each other. The table gives the median of three runs, each taken after a warm-up run.

| | Before | After |
| --- | ---: | ---: |
| Bootstrap to Home showing data | 3,657 ms | 1,452 ms |
| Tab tap to first list row | 658 ms | 238 ms |
| Scroll, build per frame: average | 29.4 ms | **5.9 ms** |
| Scroll, build per frame: p90 | 33.3 ms | 13.1 ms |
| Scroll, build per frame: p99 | 599 ms | **42.0 ms** |
| Scroll, build per frame: worst | 1,921 ms | 132 ms |
| Frames over the 16.7 ms build budget | 301 of 1,166 | 131 of 1,818 |
| Rows reached in the 30 flings | 1,350 | 1,700 |
| Cold start, engine to first frame | 3,417 ms | not re-measured |

**What a new list window costs** (`slow_build_frames_after_a_snapshot_detail`, one run each):

- Before, the build time grew with the window: 33 ms at 100 rows, 283 ms at 200, 958 ms at 600, 1,672 ms at 750, and 2,496 ms at 1,250. The
  whole window was built and laid out on every snapshot.
- After, it stays at 17–58 ms from 200 to 1,900 rows, with rare outliers at 112 and 258 ms. Only the rows near the screen are built.

**Notes:**

- Raster time on the emulator stays high in both runs: an average of 28–48 ms and over 1,000 frames over budget. That is the emulator's GPU.
  On the iPhone 15 at 10k, raster averaged 1.6 ms and no frame missed its budget.
- The faster bootstrap-to-Home time after the change also reflects the balances, which Home reads. It is the noisiest number here.
- Cold start was not run again: T6 changed nothing that runs before the first frame.

## Soundbites, with the numbers behind them

- "Account balances over 50k transactions went from 27 ms to 5 ms by widening two existing indexes into covering ones, with no extra index
  to maintain on a write" (host, repository median).
- "The transaction list's worst frame went from about 1.9 s to about 0.13 s at 50k by making each day's card a lazy sliver" (Android
  emulator, profile). Before, a new page rebuilt the whole window. After, it rebuilds a screenful.
